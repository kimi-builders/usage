# 本地版与社区版：产品和信任边界

> 决策状态：当前产品原则。改变这些边界需要同时更新 README、PRIVACY、NETWORK、协议测试与
> 用户界面文案，不能作为普通重构悄悄发生。

Kimi Builders Usage 同时服务两个产品场景：一台电脑上的私有分析，以及 kimi.builders 上的
跨设备与社区体验。它们共享 Collector 和数据口径，但不是“残缺免费版 / 完整云端版”。

## 1. 核心原则

```text
用户自己的本地数据价值 → 本地版完整提供
只有网络和多人关系才能成立的价值 → 社区提供
涉及凭据、公开身份或后台行为 → 默认关闭并明确授权
```

本地版的完整性是社区的信任基础。社区不通过扣留本地分析逼迫登录，而依靠跨设备历史、公开
身份、排行榜、成就、作品关联和群体基准形成不可替代的网络价值。

## 2. 当前能力分工

| 能力 | 本地版 | kimi.builders 社区 |
| --- | --- | --- |
| 多 Agent 扫描与统一数据口径 | 完整实现 | 接收已聚合结果，不远程扫描 |
| Token、费用、时间、趋势、自然周、热图 | 完整实现 | 完整，多设备合并 |
| 模型、项目、推理强度、Agent 版本筛选 | 本机可用 | 对已上传维度可用 |
| 明细与 CSV/JSON 导出 | 完整，本地生成 | 账户历史导出 |
| 分享海报 | 本机生成，无 localhost QR | 可生成公开可访问的分享入口 |
| 标准 API 价格估算 | 本地版本化目录 | 服务端版本化目录 |
| 订阅额度 | 本机直连所选 provider | 不接收凭据或额度响应 |
| 单设备历史 | 完整 | 完整 |
| 跨设备连续历史 | 不适用 | 核心能力 |
| 公开档案、成就、Token 排行榜 | 不适用 | 核心能力，按账户可见性 |
| 作品构建排行榜与作品关联 | 不适用 | 社区能力 |
| 讨论、关注与开发者身份 | 不适用 | 社区能力 |
| 后台同步 | 本机用户级调度器 | 只能接收，不能主动拉取 |

## 3. 三条完全独立的数据通道

### 本地 Token 看板

- 默认启用、无需账号、无需联网。
- 只读取已知 Agent 目录和用户明确提供的 Cursor CSV。
- 本地 HTTP 服务只监听 loopback，并使用每次启动随机 capability token。
- 重新扫描只刷新本机快照，不会安装 daemon 或触发上传。

### 订阅额度

- 默认总开关关闭，每个平台单独启用。
- 凭据优先复用 provider 自己的本机登录；手动 secret 只允许环境变量或支持时的系统钥匙串。
- 浏览器只得到规范化额度窗口，得不到原始 Cookie、Token 或 provider 响应。
- 额度数据不进入 Token 快照、导出、海报或社区同步。

### 社区同步

- 必须先由用户运行 `init` 完成设备授权。
- 单次 `sync` 和后台 daemon 使用同一套隐私裁剪、协议验证与 checkpoint。
- 社区无法反向要求 Collector 读取新目录、启用 provider 或上传新字段。
- 同步项目名默认关闭；同步成功也不会自动打开公开档案或排行榜可见性。

## 4. 哪些能力应当留在本地

满足以下任一条件时，优先本地实现：

- 只依赖本机已有日志或用户主动导入的文件；
- 结果是用户理解自己数据所必需的，而不是社区关系产生的；
- 涉及 provider 凭据、Cookie、额度响应或完整私有明细；
- 可以在不牺牲正确性和体验的情况下离线完成；
- 开源与可审计会显著提升用户信任。

因此 Token 计算、价格估算、筛选、明细、图表、私人导出、订阅额度和本地海报不应被云端
登录墙截断。

## 5. 哪些能力属于社区

满足以下条件时，社区比本地更合适：

- 需要多台设备长期合并和服务端持久化；
- 需要公开身份、可访问 URL、关注关系或社区声誉；
- 需要跨用户比较、群体百分位、排行榜或作品关系；
- 需要防滥用、可见性控制、撤销和账户生命周期；
- 本地单机无法提供真实价值，而不是技术上“也能做一个静态版本”。

社区的王牌不应只是本地统计的镜像，而应逐步形成：跨设备连续历史、Token Usage 排行、作品
构建排行、Agent/模型社区基准、成就、可验证的公开分享和作品上下文。

## 6. 不可突破的安全与体验红线

- 打开本地看板不能自动同步、安装后台服务或联系 provider。
- 云端不能远程配置本地扫描路径、额度凭据或 daemon。
- Prompt、response、reasoning 文本、tool result、文件内容和完整路径没有上传协议字段。
- Provider Cookie、OAuth Token、API Key、钥匙串值和原始额度响应永不进入浏览器、导出或同步。
- 项目上传和公开可见性不能捆绑授权。
- 删除远端数据不能伪装成删除本地数据；重新上传的 checkpoint 后果必须明确说明。
- 标准 API 估费必须带覆盖率与假设，不得冒充订阅账单或实际支付金额。
- 开源包来源只能读取固定已知位置；新增读取面必须写文档、fixture 和隐私测试。
- 排行榜是社区认可，不是 provider 认证的账单、生产力或工作量证明。

## 7. 当前有意保留的差异

| 场景 | 本地版选择 | 原因 |
| --- | --- | --- |
| 身份 | `LOCAL` 与浏览器本地海报名 | 无社区账户也应完整可用 |
| 导航 | 本地分析锚点 + 明确社区入口 | 不展示无法工作的社区路由 |
| 海报 | 不生成二维码或 localhost 链接 | 分享接收者无法访问本机地址 |
| 数据新鲜度 | 每次主动扫描 | 不暗示浏览器页面在后台常驻 |
| 设备 | 当前真实终端、OS、Collector、Agent 版本 | 不从 AI 来源伪造设备名 |
| 额度 | 本机直接查询 | 凭据和响应不进入社区 |
| 自定义日期 | 当前未实现 | 常用范围优先，后续按需求评估 |

## 8. 新功能的归属检查表

在实现前回答：

1. 数据来源在哪里？本机日志、provider API、社区账户还是公开数据？
2. 用户不登录时，是否仍然有权获得这项个人数据价值？
3. 是否需要新的读取目录、环境变量、Cookie、网络域名或上传字段？
4. 页面关闭后是否继续运行？谁安装、查看和移除这个行为？
5. 结果是否会公开，能否撤销，是否会暴露项目、设备或活动规律？
6. 本地和社区都实现时，哪一方是事实来源，如何避免口径漂移？
7. 是否需要更新 `PRIVACY.md`、`NETWORK.md`、本地快照、协议版本或威胁模型？

如果这些问题没有答案，功能还不能进入开发。

## 9. 近期产品方向

当前优先级不是削减本地版，而是提高两端的一致性和社区增量价值：

- 用共享 fixture/契约防止 Collector 与站点计算漂移；
- 让社区提供本地无法完成的跨设备、排名、成就和作品洞察；
- 让本地连接、同步、撤销与恢复对新手更透明；
- 保持 provider 额度完全本地，同时提高兼容性和失败说明；
- 持续以跨平台 CI、契约测试、SBOM 与 provenance 维护公开 npm 包的供应链质量。

具体执行顺序见 [ROADMAP.md](./ROADMAP.md)。
